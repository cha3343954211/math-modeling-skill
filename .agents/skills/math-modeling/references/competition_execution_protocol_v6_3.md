# 数学建模竞赛执行协议 v6.3

> 用于 L2/L3 任务：将审题、数据、模型、验证、协作与交付固化为可检查的证据链。赛事当年官方规则优先于本文。

---

## 1. Phase 1 必备文件

### 1.1 `competition_brief.md`

竞赛任务开始时填写：

```markdown
# 赛事规则卡
- 赛事/年份/组别：
- 官方赛题与规则来源：
- 题目、附件版本与下载时间：
- 截止时间与时区：
- 语言、模板、页数、匿名规则：
- 引用、附录、代码/数据提交规则：
- 提交渠道与文件命名要求：
- 未确认项与负责人：
```

### 1.2 `problem_spec.md`

每个子问题均填写下表，题干事实、建模假设和待确认事项必须分开。

| 字段 | 内容 |
|---|---|
| 对象与粒度 | 决策/预测/评价对象；时间、空间、个体粒度 |
| 输入与输出 | 变量名、单位、口径、可得时点 |
| 目标与成功标准 | 最小化/最大化/预测什么；如何评价成功 |
| 硬约束与软约束 | 每条附题干或现实来源 |
| 已知事实 | 题干明确给出、数据可验证的信息 |
| 建模假设 | 为可求解作出的简化及其理由 |
| 不确定性/不可识别项 | 缺失机制、随机扰动、无法确认的参数 |
| 与其他问题的关系 | 继承变量、变化条件、不可共用部分 |

### 1.3 数据证据链

必须建立：

- `data_dictionary.csv`：字段、含义、单位、类型、来源、时间覆盖、缺失编码、预测时点是否可获得；
- `data_processing_log.md`：删除、去重、截断、插补、标准化、单位换算等规则、影响行数和理由；
- `split_protocol.md`：训练/验证/测试或滚动窗口划分与调参规则；
- 原始数据放入 `data/raw/`，保持只读；处理后数据放入 `data/processed/`。

**防泄漏规则**：若预测/分类有时间顺序，测试集必须位于训练期之后；插补器、标准化器、特征选择器和调参过程只可在对应训练折拟合。无法满足时间外验证时，结论只能称为拟合或情景分析，不得声称外推精度。

### 1.4 假设追踪矩阵

| 假设 ID | 必要性与理由 | 对应公式/代码 | 可检验方式 | 不成立的影响 | 替代或敏感性方案 |
|---|---|---|---|---|---|

每条核心假设必须至少关联一个模型位置和一种检验/讨论方式。

## 2. 模型注册与停止规则

建立 `docs/model_registry.md`：

| 候选模型 | 适用前提 | 数据版本 | 验证协议 | baseline/对照 | 指标与耗时 | 结论/淘汰理由 |
|---|---|---|---|---|---|---|

### 最低准则

1. 主模型必须和可解释、可运行的 baseline 在相同数据口径和验证协议下比较。
2. 新模型无实际重要提升、明显更不稳定或无法解释时，保留简单模型为主方案。
3. 剩余时间不足以完成验证和写作时，冻结稳定模型，优先完善证据和论文。
4. 失败模型记录原因；不得因为结果不符合预期而隐去关键失败或挑选性汇报。

## 3. 按题型验证协议

| 题型 | 最低验证证据 | 必须避免 |
|---|---|---|
| 预测 | 时间外/滚动验证；持久性或季节性持久性 baseline；关键区间误差与误差分布 | 随机打乱时序；未来信息特征；仅报告训练集指标 |
| 优化 | 逐条约束检查；目标值与简单策略、下界或小规模精确解比较；求解器状态/最优性缺口 | 只报目标值；把启发式可行解说成全局最优 |
| 评价/排序 | 指标方向与冗余审计；权重、归一化和排序方法扰动；Spearman/Kendall、前 k 稳定性 | 权重无来源；重复计权；只报最终排名 |
| 仿真 | 参数来源/校准；重复运行、随机种子、置信区间；情景边界 | 以单次随机运行下结论；未说明分布 |
| 机理 | 量纲检查、边界/初值、参数可识别性、拟合/残差 | 任意调参使曲线“看起来合理” |
| 因果/政策 | 处理组与反事实、混杂与识别假设；不能识别时降级为关联分析 | 把相关性或预测能力写成因果效果 |

## 4. 项目脚手架与复现

```text
project/
  README.md
  competition_brief.md
  problem_spec.md
  data/{raw,interim,processed}/
  docs/{assumptions.md,model_registry.md,data_processing_log.md,split_protocol.md}/
  src/{00_audit.py,01_prepare.py,02_baseline.py,03_model.py,04_validate.py}/
  configs/
  outputs/{tables,figures,run_summary.json,frozen_numbers.json}/
  paper/
  requirements.txt 或 pyproject.toml
```

- 每张表和图必须由脚本生成；论文不得手填关键计算数字。
- `run_summary.json` 至少包含输入数据版本、脚本版本/运行时间、随机种子、参数、指标和输出路径。
- `frozen_numbers.json` 只存已确认要进入论文的数字，包含名称、值、单位、来源表/图和生成脚本。
- 提交前在独立目录或干净环境按 README 完整复跑一次。

## 5. 三人协作与交接

| 角色 | 主要责任 | 每轮输出 |
|---|---|---|
| 负责人 | 题意、问题规格、假设与全局一致性 | 风险清单、决策记录 |
| 数据/代码负责人 | 数据治理、可复现代码、验证 | 数据日志、结果表、运行摘要 |
| 论文/图表负责人 | 论文叙事、图表登记、格式 | 图表说明、可引用结论、主文版本 |

- 每 6–8 小时简短同步：已确认事实、风险/阻塞、下一交付物与负责人。
- `frozen_numbers.json` 与 `outputs/tables/` 是关键数字的唯一事实源。
- 每张图交接时提供：路径、生成脚本、数据版本、图号、可引用数字、2–4句结论和局限。
- 使用 Git 或带时间戳的版本备份；避免多人同时覆盖主论文文件。

- [ ] 每项结论可追溯至数据版本、脚本、表格/图表和假设。
- [ ] 主模型相对 baseline 的结论在同一验证协议下成立；无提升处已诚实说明。
- [ ] 优化解的约束、随机算法的重复运行、评价排序的稳定性均有证据。
- [ ] 建议可追溯至指标、阈值或情景结果，且写明适用边界。
- [ ] 从输入到关键图表/表格已独立复跑，论文数字一致。
